# Feature Specification: Weather History

**Feature Branch**: `001-weather-history`  
**Created**: 2026-03-27  
**Status**: Draft

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Просмотр истории погоды по городу (Priority: P1)

Как пользователь WeatherApp, я хочу запросить историю погоды по городу за
диапазон дат, чтобы анализировать, какая погода была ранее.

**Why this priority**: это основная ценность фичи. Без этого сценария фича
`Weather history` не существует как пользовательская возможность.

**Independent Test**: сценарий полностью проверяется одним HTTP-запросом к
новому endpoint'у истории и валидацией состава ответа.

**Acceptance Scenarios**:

1. **Given** город существует и провайдер возвращает исторические данные,
   **When** пользователь вызывает
   `GET /weather/{city}/history?start_date=2026-03-20&end_date=2026-03-22`,
   **Then** API возвращает `200 OK` и массив записей истории по каждой дате
   диапазона.
2. **Given** в истории есть три дня данных, **When** пользователь получает
   ответ, **Then** каждая запись содержит дату, температуру, погодное
   состояние и время получения данных.
3. **Given** пользователь запрашивает историю только за один день, **When**
   `start_date == end_date`, **Then** API возвращает массив из одной записи.

---

### User Story 2 - Предсказуемая обработка ошибок диапазона (Priority: P2)

Как пользователь WeatherApp, я хочу получать понятную ошибку при некорректном
диапазоне дат, чтобы быстро исправить запрос.

**Why this priority**: без этого система будет вести себя непредсказуемо и
усложнит использование API, но основная пользовательская ценность уже покрыта
User Story 1.

**Independent Test**: сценарий проверяется несколькими негативными
HTTP-запросами без необходимости поднимать полный production flow.

**Acceptance Scenarios**:

1. **Given** `start_date` позже `end_date`, **When** пользователь вызывает
   endpoint истории, **Then** API возвращает `422 Unprocessable Entity` с
   понятным сообщением о неверном диапазоне.
2. **Given** диапазон превышает допустимый лимит, **When** пользователь
   вызывает endpoint истории, **Then** API возвращает
   `422 Unprocessable Entity` и сообщает максимальную длину диапазона.
3. **Given** формат даты не соответствует ISO `YYYY-MM-DD`, **When**
   пользователь вызывает endpoint истории, **Then** API возвращает
   `422 Unprocessable Entity`.

---

### User Story 3 - Повторный запрос без лишней нагрузки на провайдера (Priority: P3)

Как владелец сервиса, я хочу повторно использовать ранее полученные результаты
исторических запросов, чтобы снизить нагрузку на внешний Weather API и ускорить
повторные ответы.

**Why this priority**: фича приносит пользу и без локального хранения истории,
но для стабильности, стоимости и масштабируемости это важное улучшение.

**Independent Test**: сценарий проверяется двумя одинаковыми запросами подряд и
контролем числа обращений к внешнему провайдеру.

**Acceptance Scenarios**:

1. **Given** история по диапазону уже была получена ранее и ещё считается
   актуальной, **When** пользователь повторяет тот же запрос, **Then** API
   возвращает данные из локального хранилища без повторного обращения к
   внешнему провайдеру.
2. **Given** часть периода уже сохранена локально, **When** пользователь
   запрашивает расширенный диапазон, **Then** система дозапрашивает только
   отсутствующие дни.

### Edge Cases

- Город существует в текущем API, но провайдер исторических данных не
  поддерживает этот регион или возвращает неполные данные.
- Пользователь запрашивает диапазон, в котором часть дат находится в будущем.
- Пользователь передаёт город с пробелами, разным регистром или URL-encoded
  символами.
- Провайдер возвращает исторические данные с шагом меньше или больше одного
  дня.
- В локальном хранилище уже есть данные по части дней, но формат ответа
  провайдера изменился.
- Провайдер временно недоступен или отвечает медленно.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставить новый endpoint
  `GET /weather/{city}/history`.
- **FR-002**: Endpoint истории MUST принимать query-параметры `start_date` и
  `end_date` в формате `YYYY-MM-DD`.
- **FR-003**: Система MUST валидировать, что `start_date <= end_date`.
- **FR-004**: Система MUST отклонять запрос, если диапазон превышает
  30 календарных дней.
- **FR-005**: Система MUST отклонять запрос, если `end_date` находится в
  будущем относительно UTC-даты сервиса.
- **FR-006**: Система MUST нормализовать значение `city` так же, как это уже
  делается в текущем weather endpoint.
- **FR-007**: Система MUST возвращать историю в виде массива дневных записей,
  отсортированных по дате по возрастанию.
- **FR-008**: Каждая запись истории MUST содержать как минимум: `date`, `city`,
  `temp`, `condition`, `humidity`, `wind_speed`, `pressure`, `fetched_at`,
  `source`.
- **FR-009**: Система MUST явно различать источник записи: `provider` или
  `cache`.
- **FR-010**: При запросе истории система MUST сначала проверять локально
  сохранённые данные и обращаться к внешнему провайдеру только за
  отсутствующими днями.
- **FR-011**: Система MUST сохранять полученные исторические данные в локальном
  персистентном хранилище для повторного использования.
- **FR-012**: Система MUST возвращать `400` или `422` только для ошибок
  валидации пользовательского запроса; ошибки внешнего провайдера MUST
  маппиться в `503`.
- **FR-013**: Если город не найден у внешнего провайдера, система MUST
  возвращать `400` с понятным сообщением, согласованным с текущим поведением
  `GET /weather/{city}`.
- **FR-014**: Система MUST логировать запрос истории с городом, диапазоном дат,
  числом записей из кэша и числом записей от провайдера.
- **FR-015**: Система MUST поддерживать unit и integration тесты для позитивных
  и негативных сценариев новой фичи.
- **FR-016**: Core business logic фичи MUST быть выделена в отдельный
  переиспользуемый модуль или сервис истории погоды, независимый от конкретного
  transport layer.
- **FR-017**: Фича MUST предоставлять интерфейс для ручного запуска запроса
  истории в text и JSON формате.

### Non-Functional Requirements

- **NFR-001**: Ответ на диапазон до 7 дней из локального хранилища SHOULD
  укладываться в 500 мс на локальном окружении разработки.
- **NFR-002**: Повторный запрос того же диапазона SHOULD выполнять не более
  одного обращения к локальному хранилищу и ноль обращений к внешнему
  провайдеру.
- **NFR-003**: При недоступности внешнего провайдера сервис MUST не терять уже
  сохранённые исторические данные.
- **NFR-004**: Все новые комментарии в коде и документация MUST быть на
  русском языке.

## Out of Scope *(mandatory)*

- Почасовая история и любая granularity, отличная от дневной, не входят в MVP
  этой фичи.
- Изменение базового поведения существующих endpoint'ов текущей погоды и
  управления подписками не входит в объём этой спецификации.
- Специализированные сценарии запроса истории по email или подписке сверх
  прямого запроса по городу не входят в текущую итерацию.
- Отдельная политика принудительного refresh уже сохранённых исторических
  записей не детализируется в рамках текущей итерации.

### Key Entities *(include if feature involves data)*

- **WeatherHistoryRecord**: одна дневная запись исторической погоды для
  конкретного города и даты. Ключевые атрибуты: `city`, `date`, `temp`,
  `condition`, `humidity`, `wind_speed`, `pressure`, `fetched_at`, `source`.
- **WeatherHistoryQuery**: входная модель запроса истории. Ключевые атрибуты:
  `city`, `start_date`, `end_date`.
- **WeatherHistoryResponse**: агрегированный ответ API для диапазона. Ключевые
  атрибуты: `city`, `start_date`, `end_date`, `records`.
- **StoredHistoricalWeather**: сущность локального хранилища для уже полученной
  истории. Ключевые атрибуты: `city`, `date`, `temp`, `condition`, `humidity`,
  `wind_speed`, `pressure`, `fetched_at`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь может получить историю погоды за 1-30 дней одним
  HTTP-запросом без обращения в support или ручной обработки данных.
- **SC-002**: Не менее 95% повторных запросов на тот же диапазон обслуживаются
  без вызова внешнего провайдера, если данные уже сохранены локально.
- **SC-003**: Все обязательные позитивные и негативные проверки сценариев
  истории проходят в стандартном pipeline контроля качества.
- **SC-004**: Время ответа на повторный запрос диапазона до 7 дней не
  превышает 500 мс на локальном стенде разработки.
- **SC-005**: Документация API и интерфейса ручного запуска истории погоды
  доступна в репозитории и достаточна для самостоятельного запуска
  разработчиком или студентом.

## Assumptions

- WeatherApp уже умеет получать текущую погоду по городу и управлять
  подписками на города.
- В MVP используется дневная история погоды; один календарный день является
  минимальной поддерживаемой единицей истории.
- Внешний провайдер исторических данных способен вернуть либо данные по
  поддерживаемому городу и диапазону, либо явную ошибку о недоступности города
  или региона.
- Сохранённые исторические данные могут повторно использоваться для одинаковых
  или пересекающихся диапазонов, пока не будет утверждена отдельная политика
  refresh.
- У приложения есть локальное персистентное хранилище, позволяющее сохранять
  историю между запросами.
